DeepSeek Harness 使用指南

写给使用者，不写给开发者。读完这一页，你会知道 dsh 是什么、怎么跑起来、 Agent / Token / 缓存命中这些词到底在说什么，以及什么样的提示词能让它把活干对。

本指南基于 DeepSeek Harness 开发者预览版（@deepseek-ai/dsh 0.1.5-rc.1） 与 DeepSeek 官方文档整理。这个项目在快速迭代，界面和价格都可能变， 涉及具体数字时请以官方文档为准。

一句话认识 dsh：它是一个「智能体框架（agent harness）」。 模型本身只会说话，dsh 给模型配上了手和脚——读写文件、执行命令、搜索网页、开子代理干活， 并且在你授权的前提下动手。它自己也是一个网页应用，跑在本机 127.0.0.1:3080。

01 · 安装与上手

这一节按 B 站视频《手把手安装 deepseek-harness》的流程整理（Windows 环境）， 视频里提到的坑点单独标了出来。

  1. 安装 Node.js dsh 本身是 Node.js 程序，必须先装运行环境，不然后面跑不起来。 到 nodejs.org 下载 LTS 版本，一路「下一步」即可。

    安装时可以顺手改路径：视频里建议把安装目录从 C 盘改到 D 盘，别把系统盘塞满。 装完在命令行输入 node -v，能显示版本号就算成功。

  2. 打开命令行 按 Win + R，输入 cmd 回车，会弹出一个黑色窗口。

    接下来的命令都在这个黑框里执行。这个黑框不能关——关掉它，dsh 就停了。

  3. 安装 dsh 本体 
    npm install -g @deepseek-ai/dsh --verbose

    末尾的 --verbose 是视频作者特意加的：它会不停打印下载日志， 不然安装过程中界面看起来像卡死，容易误以为没反应。全程需要联网，网络慢就多等几分钟。

    如果进度条一直不动、或者慢到无法接受：换成国内镜像源再执行一次（视频里给的补救办法）：

    npm install -g --registry=https://registry.npmmirror.com @deepseek-ai/dsh --verbose
  4. 启动 
    dsh web

    注意 dsh 和 web 中间有一个空格。 启动成功后浏览器会自动打开，地址是 http://127.0.0.1:3080； 如果没自动弹出来，手动在浏览器里输入这个地址即可。

  5. 填模型密钥（申请 API Key） 第一次启动时，界面会直接弹出一个让你填密钥的对话框；也可以之后从设置 → 模型进去填。 密钥在 platform.deepseek.com 申请。

    保存后模型路由立刻可用，不需要重启服务。

  6. 选择工作区 点击选择工作区，把项目目录添加进来并选中。

    工作区就是 Agent 的「办公桌」——它默认只能在这张桌子上翻箱倒柜。 注意：没选中工作区之前，输入框是不可用的。 路径尽量用英文命名，中文路径在个别环节容易出问题。

  7. 发第一个任务 新建会话，直接说人话，例如： 
    帮我通读这个项目，告诉我它有哪些主要模块，各自负责什么。先不要改任何文件。
  8. 看懂「审批」 当某个操作需要你点头时，界面会停下来问你。同意它就继续，拒绝它就换条路走。

    这是安全设计，不是卡住了。你随时可以撤销授权或改变策略。

想双击就打开？做个桌面快捷方式

每次都开黑框敲命令太麻烦。视频最后一段给了个很实用的做法：

  1. 桌面右键 → 新建 → 文本文档。
  2. 打开它，把 dsh web 这一行粘进去，保存并关闭。
  3. 把文件名后缀从 .txt 改成 .bat（需要先在文件资源管理器里打开「查看 → 显示 → 文件扩展名」才改得动）。
  4. 双击这个 .bat，dsh 就启动了。

两个常见坑：

  • 双击闪退或打不开：多半是之前那个黑框还开着（dsh 已经在运行）。先把旧黑框关掉，再双击。
  • 想换图标：右键该文件 → 属性 → 更改图标即可，也可以自己把图片转成 .ico 再选。

另一种安装方式（免安装）：官方 README 给的是 npx @deepseek-ai/dsh web——不装进电脑、每次临时下载运行， 适合只想试一次的人；缺点是每次启动都要重新下载，比较慢。 打算长期用，还是推荐上面这种全局安装。

第一次使用请先记住三条：

  • 它会真的改你的文件、真的执行命令，所以重要资料先备份或者在别处试。
  • 不确定的活，就告诉它「先只读不改」，看它分析得对不对再放行。
  • API Key 是花钱的钥匙，不要贴进聊天内容里，也不要提交到代码仓库。

02 · 几种启动方式

同一个 dsh，换个参数就是另一种用途。刚上手只需要知道第一种。

命令用途适合谁
dsh web 启动网页界面，日常使用的主入口 所有人
dsh --profile headless "任务" 跑一个一次性会话，把最终答案打印出来就退出 想写进脚本、定时任务的人
dsh --profile acp 通过 ACP 协议为编辑器等自动化客户端提供服务 把 dsh 当后端接进别的工具
dsh --profile sdk 通过 JSON-RPC 为 SDK 客户端提供服务 用代码调用 Agent 的开发者
dsh plugin --profile web <pnpm 参数> 给某个 profile 安装或卸载插件 想扩展功能的人

「profile」是 dsh 的一种启动配置集合（可以理解成「预设」）。不同的 profile 装载不同的插件组合， 互不干扰，所以你能一边用网页版，一边写脚本用无头版。

03 · 基础词汇

下面这些词，你会在聊天记录、教程和报错里反复看到。每条都给你一句人话解释和一个比喻， 看不懂的部分可以跳过，用到的时候再回来查。

智能体Agent

不只是「会聊天的模型」，而是能自己规划步骤、调用工具、看结果、再决定下一步的模型。

实习生。你交代目标，他自己找路径干活，中间会来问你拿主意。

框架Harness

给模型装上「手和脚」的那层外壳：工具、权限、记忆、界面都归它管。dsh 就是 DeepSeek 的 harness。

工人的工位和工具台。模型是工人，Harness 决定他能拿到哪些工具。

模型与服务商Model / Provider

模型是「大脑」（如 deepseek-flash、deepseek-v4-pro），服务商是提供这个大脑的公司或接口地址。

模型是发动机型号，服务商是加油站。

TokenToken

模型读写文字的最小计费单位，可以粗略当成「字」或「词」。输入和输出都按 token 数收钱。

打车的「公里数」。内容越长，跳表越快。

上下文 / 上下文窗口Context / Context Window

模型这一次能看到的所有内容：系统提示、历史对话、你贴的文件、工具返回的结果。窗口就是上限。

摆在桌面上的材料。桌子只有这么大，摆满了就得收走一部分旧纸。

系统提示词System Prompt

每次请求都排在最前面的固定说明，规定它的身份、规矩和可用工具。用户一般不用自己写。

员工手册的第一页，每天上班都先读到它。

工具 / 工具调用Tool / Tool Call

模型能调用的具体能力，比如读文件、跑命令行、搜网页。模型不直接执行，而是「提出调用」，由程序执行后把结果还给它。

点外卖。它只能下单，饭是骑手（程序）送来的。

技能Skill

预置的专业操作手册，遇到特定任务时才加载进上下文，避免每次都把一大本说明书塞给它。

工具箱里贴了标签的专项手册，用到哪本抽哪本。

审批Approval

敏感操作（删文件、装软件、联外网）前先征求你同意的机制。你可以在界面上同意或拒绝。

财务报销要签字。金额越大，越需要你本人点头。

沙箱Sandbox

限制 Agent 活动范围的围栏。比如「只能改工作区里的文件」，出了圈就会被拦下并报错。

儿童活动区的软围栏。撞上去不会受伤，但也过不去。

会话 / 工作区Session / Workspace

会话是一次连续的对话（有记忆、能恢复）；工作区是它允许读写的目录范围。

会话是「这次会议」，工作区是「这间办公室」。

插件Plugin

dsh 的功能单元。它的设计理念是「一切皆插件」——工具、界面、模型接入都是插件，可以增删和组合。

乐高积木。整台机器由一块块积木拼出来，也能拆下来换掉。

预设 / ProfilePreset / Profile

一整套插件与配置的打包。换一个 profile，就换了一套能力组合，彼此不影响。

不同的工作模式：办公模式、游戏模式、省电模式。

子代理Subagent

主 Agent 派出去的小分队。它有自己的上下文，干完只回报结论，不把过程垃圾倒回主对话。

派同事去仓库盘点，回来只交一张清单。

计划 / 待办 / 目标Plan / Todo / Goal

三种管进度的手段：计划是先写方案给你审，待办是任务清单，目标是跨多轮持续推进的一件大事。

计划是施工图，待办是今日清单，目标是「这个月盖完这栋楼」。

上下文压缩Compaction

对话太长、快塞满窗口时，把旧内容总结成摘要，腾出空间继续干。

笔记本写满了，先抄一页重点，再撕掉草稿。

推理强度Reasoning Effort

模型「想多久」的档位。调高更擅长复杂推理，但更慢更贵；调低更快更省，适合简单任务。

考试时打草稿的认真程度。

温度Temperature

控制输出随机性的参数。低温度更稳定保守，高温度更发散有创意。日常干活一般用默认值就好。

做菜的「火候」：小火稳定，大火出花但也容易翻车。

幻觉Hallucination

模型一本正经地说错话，比如编造不存在的函数名、文件和引用。

自信的实习生凭印象写报告，没去查原始资料。

缓存命中Cache Hit

这次请求的输入前缀，和之前某次请求重复，重复部分可以直接从缓存读取，价格便宜很多。

同一份资料第二次复印，不用重新排版，直接过机。

04 · Token 与费用

Token 到底是什么

Token 是模型处理文字的最小单位，也是计费单位。它不等于「字」，因为模型有自己的切词方式。 官方给出的换算经验值是：

  • 1 个英文字符 ≈ 0.3 个 token
  • 1 个中文字符 ≈ 0.6 个 token

也就是说，1000 个汉字大约是 600 个 token。不同模型切词方式不同， 精确数字以接口返回结果里的 usage 字段为准。

三个容量数字

项目数值说明
上下文长度1M tokens模型一次能「看到」的总上限，约合一百六十多万汉字
最大输出长度384K tokens单次回答能写多长
计费口径输入 + 输出输入按缓存是否命中分两档计价，输出单独一档

价格对照（2026-09-16 官方页面）

单位：元 / 百万 tokens。空闲时段为高峰时段的一半，高峰时段是北京时间周一至周五 9:00–12:00、14:00–18:00。

模型输入（缓存命中）输入（缓存未命中）输出
deepseek-flash · 空闲0.0214
deepseek-flash · 高峰0.0428
deepseek-v4-pro · 空闲0.154.513.5
deepseek-v4-pro · 高峰0.309.027.0

模型名称与价格可能调整。较新的模型名请以官方「模型 & 价格」页面为准。

费用怎么算：一个真实例子

公式很简单：

费用 = 命中 token 数 × 命中单价
     + 未命中 token 数 × 未命中单价
     + 输出 token 数 × 输出单价

假设一次任务：输入 20 万 tokens（其中 19 万命中缓存、1 万未命中），输出 5000 tokens，用 deepseek-flash 的空闲时段价格：

  • 命中：190,000 ÷ 1,000,000 × 0.02 = 0.0038 元
  • 未命中：10,000 ÷ 1,000,000 × 1 = 0.01 元
  • 输出：5,000 ÷ 1,000,000 × 4 = 0.02 元
  • 合计约 0.034 元

注意这里的对比有多悬殊：19 万个命中 token 只花了 0.0038 元， 而 1 万个未命中 token 花了 0.01 元。省钱的真正抓手是缓存命中率，不是少问几句话。

省钱五条

  1. 同一个话题别开新会话。新会话等于缓存全部作废，前面读过的文件要重新算一遍钱。
  2. 任务描述一次给足。挤牙膏式提问会让模型反复重读上下文，每一轮都在重复付费。
  3. 简单活用快模型、低推理强度。别拿大炮打蚊子。
  4. 长任务拆成几步。每步都有明确产出，出错时不用从头再来。
  5. 避免无意义的超长粘贴。贴之前先删掉无关部分，或者直接让它自己去读那个文件（读文件的结果同样能被缓存复用）。

05 · 缓存命中：最容易被忽略的一笔钱

核心结论：DeepSeek 的上下文硬盘缓存默认对所有用户开启， 你不需要改任何设置。命中缓存的输入 token，单价大约只有未命中的 1/50。

它是怎么工作的

每一次请求都会触发缓存构建。如果这次请求和之前某次请求在前缀上重复， 重复的部分就能直接从硬盘缓存读出来，这部分计入「缓存命中」。 关键在于：缓存按「缓存前缀单元」整块匹配，必须完整对上才算命中，对上九成也不算。

缓存什么时候落盘

  • 请求结束位置落盘：每次请求的「用户输入结束处」和「模型输出结束处」各形成一个缓存前缀单元。后续请求完整匹配到它就能命中。
  • 公共前缀检测落盘：系统发现多次请求有共同前缀时，会把这个公共前缀单独存成一个单元。
  • 按固定 token 间隔落盘：超长输入或输出中，系统会隔一段 token 就切一个单元存下来，避免长内容因为没走到结尾而完全无法被利用。

两个例子，一看就懂

例一：多轮对话 → 直接命中

第 1 轮你发了 A + B。

第 2 轮你继续追问，请求内容是 A + B + C。

因为 A + B 完整匹配了上一次的前缀单元，这一部分命中缓存，只有 C 是未命中的。

例二：换问题 → 要等一轮才命中

第 1 轮 A + B；第 2 轮 A + C。

A + C 对不上 A + B，两轮都不命中。

但系统会识别出公共前缀 A 并落盘。等到第 3 轮发 A + D 时，A 就能命中了。

例二的场景很典型：你上传一份长资料，然后反复问不同的问题。 前一两轮看不到便宜，从第三轮开始就明显划算了——所以别问一次就换资料，把同一份资料用透。

怎么提高命中率

  1. 稳定的内容放在前面。系统提示、规则、固定的背景资料都应排在前面，变化的问题放在最后。
  2. 别频繁改动前置内容。改一个字，后面整段前缀都对不上，全部重新计费。
  3. 在同一个会话里延续话题。历史消息天然构成可命中的前缀。
  4. 一次把材料给全。让它的输入前缀尽快稳定下来，之后的轮次都在复用它。
  5. 不要为了「干净」而频繁重开会话。追求干净界面的代价可能是重复付费。

四个常见误解

误解事实
命中缓存 = 回答是复制粘贴的缓存只作用于输入前缀，输出仍然是实时推理算出来的，受随机性影响，效果与不用缓存完全一致
缓存一定会命中缓存是「尽力而为」，不保证 100% 命中
缓存会一直留着缓存不再使用后会自动清空，通常是几个小时到几天
命中率低就是系统有 bug多数情况是使用习惯造成的：频繁改前置内容、频繁开新会话、反复换材料

在哪里看命中率

不用自己算：dsh 界面底部就有一条状态栏，实时显示当前会话的速度、缓存命中率和 token 用量。 刚开始聊第一轮时，那里会显示 Cache hit 0%——因为还没有任何历史可复用； 继续在同一个会话里追问，这个数字才会涨起来。

想更精确地核算成本，可以看 API 返回的 usage：prompt_cache_hit_tokens（命中的 token 数） 与 prompt_cache_miss_tokens（未命中的 token 数）。

06 · 怎么写提示词

提示词（Prompt）就是你发给它的那段话。好消息是：和 Agent 打交道， 比和「只会聊天的模型」打交道简单——因为它能自己去查、自己动手， 你不需要把所有资料都塞进一段话里。

一个够用的公式：

目标（要什么结果） + 范围（动哪里、别动哪里） + 约束（怎么做、不能怎么做） + 验收（怎样算做完）

反面例子 vs 正面例子

例子一 · 改代码

「帮我优化一下这个项目。」

没说优化什么、动哪个目录、能不能重构、怎么算优化完。它只能猜，猜错你还得返工。

例子一 · 改代码

「把 src/utils/date.ts 里的日期格式化函数改成支持时区参数，保持原有函数签名兼容。

只改这个文件，不要动测试。

改完跑一遍 npm test，把命令和输出贴给我。」

例子二 · 查资料

「帮我查一下 AI 相关的最新进展。」

范围太大，结果一定是泛泛而谈，而且很难判断真假。

例子二 · 查资料

「查一下 2026 年国内主流大模型的上下文长度和定价，做成表格。

每条都要给出来源链接，注明查到的日期。

查不到的直接写『未找到』，不要推测。」

例子三 · 排错

「报错了，怎么办？」

没有报错原文、没有环境、没有复现步骤，只能靠猜。

例子三 · 排错

「运行 npm run build 报错，完整报错是：（粘贴原文）

先分析原因，列出可能的几种，再挑最可能的一个去验证。

确认原因之前不要改代码。」

在 dsh 里特别有用的六个技巧

  1. 用 @ 引用文件，别靠嘴描述。 在输入框里用 @ 选中工作区里的文件或目录，它就能精确读到你指的东西， 比「那个配置文件」这种说法靠谱得多。
  2. 让它「先读后改」。 说一句「先读完相关文件，复述你的理解和修改计划，等我确认再动手」， 能挡掉大量返工。
  3. 要证据，不要结论。 要求它贴出实际执行的命令和原始输出。说「我改了」和「这是命令输出」，可信度完全不同。
  4. 明确禁止项。 「不要动 docs/」「不要升级依赖版本」「不要删除任何文件」—— 写出禁止项比写一百句鼓励有用。
  5. 给验收标准。 「测试全绿才算完成」「表格里每个数字都要有出处」，它就知道什么时候该停。
  6. 复杂任务让它先列计划。 多步骤的活先要一份计划，你审一遍再放行，比中途发现方向错了要省太多。

迭代三招

  • 指出具体错误，别只说「不对」。「第三行的公式用错了列，应该是 D 列不是 C 列」远好于「结果不对」。
  • 一次改一个变量。同时提五条修改意见，你很难判断是哪一条起了作用。
  • 让它复述需求。大任务开始前说「先用三句话复述你要做什么，我确认后你再动手」，能提前暴露误解。

09 · AI 是怎么回事

这一节不教技巧，只讲原理。理解了它，前面那些"注意事项"你就知道为什么了。 下面说的都是目前业界比较主流的看法。

它本质上只做一件事：猜下一个词

大语言模型的工作方式，是根据前面所有的文字，算出下一个 token 最可能是什么， 接上去，然后再算下一个。它不是在数据库里检索现成答案，而是在「续写」。

这是理解它一切优点和毛病的钥匙。它写得像模像样，是因为读过海量文本、学到了语言的统计规律； 它胡说八道，也是同一个原因——它被优化的目标是「接得像」，不是「说得对」。

三个原理性的限制（不是 bug，是原理决定的）

限制表现你该怎么办
幻觉 一本正经地编造不存在的函数、文件、法条、引用，语气还特别自信 涉及事实的地方要它给出处；关键结论自己复核一遍
知识有截止时间 训练数据到某个时间点为止，之后发生的事它不知道 让它联网去查，或者干脆把资料直接给它
没有真正的记忆 换个新会话，它就不认识你了 把长期规则写进 AGENTS.md，把结论落成文件

几个主流共识

  • 它是工具，不是人。它没有意图、没有情绪，也不会「故意骗你」。 它信口开河，只是因为统计上那些词最可能接在一起。
  • 它和搜索引擎不是一回事。搜索引擎给你「链接 + 出处」，让你自己判断； 它直接给你「一段听起来合理的话」。所以查事实用搜索，做整理和动手用 AI，各干各的活。
  • 它不会「越用越懂你」。模型参数在训练时就固定了，你和它聊天并不会改变它。 你感觉它变聪明，通常是因为同一个会话里上下文变长了，或者你写的规则文件被加载了。
  • 它到底「懂不懂」，业界还在吵。批评者有个著名比喻叫「随机鹦鹉」—— 看似会说话，本质是在复述训练数据里的统计模式；另一派认为规模大到一定程度后确实涌现出了新能力。 这个争论目前没有定论。你不需要站队，只要记住别把它当权威。
  • 「AI 不会取代你，但会用 AI 的人会」——这句话很流行，但更像激励话术。 更实际的说法是：它先替代的是任务，而不是职业； 它放大的是会用的人的能力。

那该怎么和它相处

  1. 给足上下文。它不知道的事不会主动问你——它会直接编。你不说的，它就自己猜。
  2. 要证据，不要结论。让它贴出命令、输出、来源链接，而不是一句「我做好了」。
  3. 关键结论自己复核。数字、法规、医疗、合同、代码正确性，这几类尤其要。
  4. 你是最终责任人。它写的东西署你的名，出错也是你的责任。这条比任何提示词技巧都重要。

一句话总结这一节：它是一个「很会接话」的概率机器； 配上 dsh 给的读写文件和执行命令的能力，就能替你干不少活。 用得好不好，关键往往不在它多聪明，而在于你给的信息够不够清楚、验收够不够严。

10 · 常见问题

它为什么不动手，一直问我？

通常是两种情况：一是当前权限策略要求敏感操作必须审批，它在等你点头； 二是你的指令本身有歧义，它在确认方向。 想少被打断，就在指令里把范围和验收讲清楚；权限策略本身也可以调整（在设置或配置层）， 但要清楚：放宽意味着风险更大。

它说改了，但我看文件没变化？

常见原因有三个：一是改动被沙箱拦下了（会报权限错误，不是静默失败，注意看输出）； 二是它只给了方案还没执行；三是改到了别的工作区或别的路径。 最有效的办法是让它贴出实际命令和原始输出，或者让它重新读一遍那个文件确认内容。

会话越聊越慢、越聊越贵，正常吗？

正常。每一轮都要把历史上下文重新送进模型，历史越长，输入 token 越多。 好消息是历史部分通常能命中缓存，单价低很多。 如果确实太长了，可以开个新会话，把关键结论复制过去；或者让它把当前进展总结成一份文件再继续。

为什么同一个任务，两次给的答案不一样？

模型输出带有随机性，缓存只复用输入，不固定输出，所以这属于正常现象。 想要更稳定的结果，可以让它把结论写进文件，后续都基于文件工作，而不是靠对话记忆。

它能联网吗？

可以，前提是当前会话给它装了联网相关的工具（网页搜索、网页抓取）。 另外要注意：联网拿回来的内容是外部数据，里面可能藏着试图操纵它的指令 （这叫提示注入）。正规的框架会把这类内容当资料处理，而不是当命令执行。

我该信任它的输出吗？

把它当成一个效率很高、但需要抽查的同事。凡是涉及事实、数字、代码正确性的部分， 都值得看一眼来源或自己验证一遍。它的强项是执行和整理，不是替你做最终判断。

深色模式和浅色模式哪个省 token？

都不省。界面的颜色和模型计费没有任何关系——之所以把这个问题写在这里， 是因为它确实经常被人认真地问。

怎么看懂网上的教学视频？

视频适合建立直觉，但更新往往滞后，容易把旧界面、旧模型名当成本次版本的事实。 建议的用法是：用视频理解概念，用官方文档核对细节。 搜索时可以用「DeepSeek Harness 入门」「dsh 插件」「prompt caching 缓存命中」这类关键词。

11 · 安全与好习惯

给它定规矩：AGENTS.md

dsh 支持把长期有效的规则写进指令文件（例如用户目录下的 ~/.dsh/AGENTS.md）， 每次开始新会话时会自动加载。你可以在这里写清楚：

  • 禁止项：比如「不要删除任何文件」「不要修改注册表」「不要强制结束某进程」。
  • 需要先问的事：比如「覆盖已有文件前必须先问我」。
  • 做事方式：比如「每步都贴出实际命令和原始输出」「出错先贴原文给我看」。

写规则的原则是：宁可具体，不要抽象。 「小心一点」没有用，「删除文件前必须问我」才有用。

权限：够用就好

  • 文件权限从「只读」开始，确认可靠后再逐步放宽。
  • 重要目录（系统盘、程序安装目录）尽量排除在工作区之外。
  • 定期看一眼它到底改了哪些文件，尤其是批量的改动。

密钥与隐私

  • API Key 只填在设置里，不要贴进聊天内容，也不要在截图里露出来。
  • 不要让它把密钥写进代码或配置文件；如果不小心写了，立刻去平台重置密钥。
  • 敏感数据要么脱敏，要么改成让它处理本地文件而不上传内容。

动手前的三个习惯

  1. 先备份。尤其是批量改名、批量格式化这类不可逆操作。
  2. 先只读。让它先分析、给方案，你确认了再执行。
  3. 要证据。命令输出、测试结果、文件 diff，比任何口头保证都可靠。
